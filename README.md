# بوت واتساب الذكي

### حالة CI
يتم تشغيل الاختبارات تلقائيًا عبر GitHub Actions على كل `push` أو `pull_request`.
[![Node.js CI](https://github.com/AbdulwahabMohammed/whatsapp-bot/actions/workflows/node-test.yml/badge.svg)](https://github.com/AbdulwahabMohammed/whatsapp-bot/actions/workflows/node-test.yml)

## مقدمة
هذا المشروع يوفر هيكلًا لبناء بوت خدمة عملاء على واتساب، معتمد على OpenAI Assistants API.
يهدف البوت إلى إدارة المحادثات والرد على استفسارات العملاء اعتمادًا على الملفات المرجعية الخاصة بكل منشأة.
يتطلب تشغيل المشروع وجود Node.js بإصدار 18 أو أحدث.
يدعم البوت أيضًا استقبال الصور والمستندات وحفظها في مجلد `uploads/` لعرضها لاحقًا من لوحة الإدارة.
## المتطلبات
- Node.js 18 أو أحدث
- قاعدة بيانات PostgreSQL
- Redis 6.2.0 أو أحدث (يُوصى باستخدام الصورة الرسمية [redis:7-alpine](https://hub.docker.com/_/redis) أو تشغيلها محليًّا عبر الأمر `docker run -p 6379:6379 redis:7-alpine`)
- الحزم التالية الموجودة في `package.json`:
  - openai@^5.9.0
  - pg
  - dotenv
  - @whiskeysockets/baileys
  - @hapi/boom
  - qrcode-terminal
  - winston-daily-rotate-file

## خطوات التثبيت والتشغيل
1. نسخ الملف `.env.example` إلى `.env` وتعبئة مفاتيح OpenAI وبيانات PostgreSQL،
   مع تحديد متغيرات `ADMIN_PASSWORD` و`ADMIN_PORT` و`SESSION_SECRET` للوحة الإدارة.
   يجب أن تكون قيمة `SESSION_SECRET` فريدة وغير "secret"، وسيُوقِف الخادم التشغيل تلقائيًا إذا تُرك هذا المتغير فارغًا.
   يمكن كذلك تعديل `SUMMARY_MESSAGE_LIMIT` لتحديد عدد الرسائل قبل تلخيص المحادثة،
   وضبط `BULK_MESSAGE_DELAY` لتعيين الفاصل الزمني بين الرسائل الجماعية،
   وضبط إعدادات السجلات عبر المتغيرات التالية:
   - `LOG_LEVEL`: يحدد المستوى الافتراضي لجميع السجلات (افتراضيًا `info`).
   - `LOG_FILE_LEVEL`: يحدد أقل مستوى يُكتب في الملفات الدورية (يستخدم قيمة `LOG_LEVEL` عند عدم تحديده).
   - `LOG_MAX_SIZE`: الحد الأقصى لحجم الملف الواحد قبل التدوير (افتراضيًا `20m`).
   - `LOG_MAX_FILES`: عدد ملفات `app-%DATE%.log` المحتفظ بها (افتراضيًا `14d`).
   - `LOG_ERROR_MAX_FILES`: مدة الاحتفاظ بملفات `error-%DATE%.log` (افتراضيًا `30d`).
   - `LOG_CONSOLE_LEVEL`: مستوى السجلات المطبوعة على الطرفية أثناء التطوير.
   أضفنا ملف إعداد جديد باسم `.env.dev.example` يحتوي على قيم مناسبة للتطوير السريع،
   ويمكن نسخه إلى `.env` عند الحاجة لاختبار البوت محليًّا بسرعة أعلى.
   **ملاحظة:** تأكد من أن المتغير `OPENAI_API_KEY` يحتوي على مفتاح صحيح من
   [منصة OpenAI](https://platform.openai.com/account/api-keys) قبل تشغيل أي أوامر
   إدارية مثل `npm run admin`، وتجنب استخدام القيم التجريبية أو `your-openai-key`.
   في حال ترك هذا المتغير فارغًا أو تمرير قيمة غير صالحة فسيقوم الملف `src/openai.js`
   الآن برمي استثناء بدلاً من إنهاء العملية مباشرة، وستقوم الوحدات التي تعتمد على
   OpenAI (مثل `chat` و`assistant` و`worker`) بتسجيل تحذير وتعطيل وظائفها المرتبطة
   حتى يتم توفير مفتاح صالح.
2. تثبيت الاعتمادات:
   ```bash
   npm install
   ```
3. تشغيل ترحيلات قاعدة البيانات:
  ```bash
  npm run migrate
  ```
ينفّذ هذا الأمر إطار الترحيلات `node-pg-migrate` لتوليد جميع الجداول والمؤشرات داخل معاملة واحدة،
كما يعيد إنشاء المستخدم الافتراضي `admin` عند توفر المتغير `ADMIN_PASSWORD`.
يمكن تشغيل الأمر مرارًا عند تحديث المخطط أو لإعادة التحقق من البنية، فهو يعيد تطبيق الترحيلات الناقصة فقط بدون تكرار للعمليات السابقة.
4. تشغيل المثال الأساسي (يشغّل `src/index.js` لإضافة منشأة تجريبية ثم عرض جميع المنشآت):
   ```bash
   npm start
   ```
5. إنشاء مساعد OpenAI لمنشأة معينة:
   ```bash
   node src/scripts/createAssistant.js <organizationId>
   ```
   يمكن تحديد نص التعليمات الخاص بالمنشأة عبر لوحة الإدارة أو مباشرة في الجدول، وسيتم استخدامه عند إنشاء المساعد أو تحديثه.
6. رفع ملف مرجعي وربطه بالمساعد:
   ```bash
   node src/scripts/uploadFile.js <organizationId> <path/to/file>
   ```
   يتحقق النظام الآن من محتوى الملف قبل رفعه إلى متجر المتجهات. إذا كان النص مطابقًا
   تمامًا لتعليمات النظام الخاصة بالمساعد (بما في ذلك التعليمات الافتراضية)، يتم تجاهل
   عملية الرفع وتسجيل تحذير في السجلات حتى لا تتسرب هذه التعليمات للعملاء. يُنصح بعدم رفع
   ملفات تحتوي على نص التعليمات مباشرة، وسيعمل الفلتر التلقائي على حجب أي رد يحاول إعادة
   إرسال تلك التعليمات للمستخدم النهائي.
   
   **أنواع الملفات المسموح بها:**
   - `.txt` (‎`text/plain`)
   - `.md` و`.markdown` (‎`text/markdown` و`text/plain`)
   - `.pdf` (‎`application/pdf`)
   - `.csv` (‎`text/csv` و`application/vnd.ms-excel`)
   - `.json` (‎`application/json`)
   - `.docx` (‎`application/vnd.openxmlformats-officedocument.wordprocessingml.document`)

   لن تُقبل أي امتدادات أو أنواع MIME أخرى، كما أن الحد الأقصى لحجم الملف الواحد هو **10 ميغابايت**.
   ستعرض لوحة التحكم ورسائل الخطأ التفاصيل نفسها عند محاولة رفع ملف غير مدعوم أو يتجاوز الحد المسموح.

   ### وضع FAST_DEV وخيارات الضبط السريع

   - `FAST_DEV=true`: يفعّل وضع التطوير السريع، ويُقلِّص عدد محاولات الاستعلام عن حالة الـ Threads
     (`RUN_MAX_RETRIES=20`) مع تقليل فترات الانتظار (`RUN_INITIAL_DELAY_MS=300` و`RUN_MAX_DELAY_MS=1500`
     ونسبة النمو `RUN_DELAY_GROWTH=1.15`).
   - عند تفعيل `FAST_DEV` من دون تحديد هذه المتغيرات يدويًّا ستُطبَّق القيم السابقة تلقائيًّا،
     بينما تظل القيم الإنتاجية كما هي عندما يكون `FAST_DEV` غير مفعّل.
   - يمكن تعطيل الكشف الآلي عن اللغة عبر `DETECT_LANGUAGE=false` (مفعّل تلقائيًّا في `.env.dev.example`)
     ليستخدم المساعد لغة المنشأة مباشرةً.
   - يعيد وضع التطوير السريع جدولة إعادة الاتصال بالواتساب كل `CONNECTION_RETRY_DELAY=1000` ميلي ثانية
     بدلًا من 5000، ويوقف الانتظار بين الرسائل الجماعية (`BULK_MESSAGE_DELAY=0`).
7. تشغيل بوت واتساب (يُحمِّل جميع المنشآت تلقائيًّا):
   ```bash
   npm run whatsapp
   ```
   في أول تشغيل ستظهر صورة QR في الطرفية لربط حساب واتساب.
يعمل البوت على كافة المنشآت المسجلة في قاعدة البيانات والتي تحتوي على معرف مساعد. يمكن كذلك بدء أو إيقاف كل بوت من لوحة الإدارة ضمن صفحة "Bots" الخاصة بكل منشأة، حيث يُعرَض رمز QR في الواجهة لربط الحساب.

8. تشغيل واجهة الإدارة:
   ```bash
   npm run admin
   ```
   يشغِّل هذا الأمر الخادم عبر الدالة `startAdminServer()` في `src/admin.js`.
   تتطلب الواجهة تعيين المتغيرين `ADMIN_PASSWORD` و`ADMIN_PORT` في ملف البيئة.
بعد تشغيل الخادم سجِّل الدخول بحساب `admin` ثم يمكنك تفعيل المصادقة الثنائية من صفحة "Profile" إن أردت.
من الصفحة نفسها يمكن تعطيل 2FA لاحقًا.
بعد ذلك يمكن إدارة المستخدمين عبر صفحة `/users` وتعديل أدوارهم بين `admin` و`editor`.
يمكن كذلك البحث في سجل الرسائل من خلال صفحة `/messages` مع إمكانية تصدير النتائج بصيغة CSV أو PDF.
توفر الواجهة أيضًا صفحة `/analytics` التي تعرض متوسط زمن الاستجابة بين استلام الرسالة وإرسال الرد يوميًا، إضافة إلى صفحة `/stats` لمراقبة حالة الاتصال وعدد الرسائل.
تُحقَن جميع نماذج لوحة الإدارة الآن بحقول `_csrf` وتُرفق الترويسة `X-CSRF-Token` في الردود لضمان حماية الطلبات من هجمات تزوير الطلبات عبر المواقع. عند كتابة اختبارات أو عملاء مخصصين يجب استخراج الرمز من صفحة `GET` المناسبة وإرساله مع أي طلب `POST` أو `fetch`.
من قائمة المنشآت يمكن اختيار "Edit Hours" لضبط قيم `working_hours_start` و`working_hours_end` الخاصة بكل منشأة، ويجيب البوت تلقائيًّا بالرسالة الموجودة في `instructions` خارج هذه الساعات.

لإنشاء حساب خاص بمنشأة معيّنة انتقل إلى صفحة `/users` واختر الدور `editor` وحدد رقم المنشأة في الحقل المخصص. عند تسجيل الدخول يظهر للمستخدم قسم "Bots" ضمن المنشأة حيث يمكنه إنشاء البوتات وتشغيلها أو إيقافها. عند بدء التشغيل يُعرض رمز QR في الواجهة وفي الطرفية وتُحفَظ الجلسة في مجلد `auth-<botId>` لإعادة استخدامها عند إعادة التشغيل. إذا ظهرت حالة `conflict` فهذا يعني أن الجلسة استُبدلت من جهاز آخر؛ احذف هذا المجلد ثم أعد تشغيل البوت لمسح رمز QR جديد.

9. التحقق من جاهزية البيئة قبل تشغيل العامل:
  ```bash
  npm run check-env
  ```
  يتحقق هذا الأمر من اتصال PostgreSQL وRedis بالإضافة إلى وجود مجلدات جلسات واتساب (`auth-*`).
  في حال رصد مشكلة سيعرض رسالة واضحة توضح الاعتماد المفقود أو غير المتوفر قبل بدء العامل.

10. تشغيل عامل المعالجة:
  ```bash
  npm run worker
  ```
  **ملاحظة:** يجب عدم تشغيل `npm run whatsapp` و`npm run worker` في الوقت نفسه
  للحساب ذاته، لأن مكتبة Baileys ستقطع الاتصال برسالة "Stream Errored
  (conflict)" عند اكتشاف تعارض.
  يتأكد العامل عند بدء التشغيل من أن خادم Redis يعمل بإصدار 6.2.0 على الأقل،
  وسيُوقف التنفيذ برسالة واضحة إذا اكتشف إصدارًا أقدم لضمان توافق أوامر BullMQ.

11. توليد اقتراحات الأسئلة المتكررة:
 ```bash
  npm run generate-faq
  ```

## إعداد السجلات

- تنشئ وحدة `src/logger.js` مجلد `logs/` تلقائيًّا إذا لم يكن موجودًا، وتكتب جميع الرسائل بصيغة JSON تحتوي على الحقول `timestamp`
  و`level` و`message` إلى جانب أي بيانات إضافية تُمرَّر مع الاستدعاء.
- تُدوَّر الملفات باستخدام `winston-daily-rotate-file` بحيث يُنشأ ملف يومي باسم `app-%DATE%.log` لرسائل المستوى `info` وما فوق مع ضغط
  الأرشيف والاحتفاظ بآخر 14 ملفًا بحجم أقصى 20 ميغابايت لكل ملف (يمكن تعديل القيم عبر متغيرات البيئة).
- تُحفظ الأخطاء أيضًا في ملفات يومية منفصلة `error-%DATE%.log` مع الاحتفاظ الافتراضي بآخر 30 ملفًا لتسهيل التحقيق في الحوادث.
- يمكن ضبط مستويات السجلات وحجم الاحتفاظ عبر المتغيرات `LOG_LEVEL` و`LOG_FILE_LEVEL` و`LOG_MAX_SIZE` و`LOG_MAX_FILES`
  و`LOG_ERROR_MAX_FILES`، كما يمكن التحكم في مستوى سجل الطرفية أثناء التطوير عبر `LOG_CONSOLE_LEVEL`.

## بنية المجلد `src/`
- `db.js` – إعداد اتصال PostgreSQL.
- `openai.js` – تهيئة عميل OpenAI ليعمل مع الإصدارات المختلفة.
- `initDb.js` – تشغيل ترحيلات `node-pg-migrate` وإعادة تهيئة المستخدم الإداري الافتراضي.
- `assistant.js` – إنشاء المساعد وإدارة ملفات المرجع.
- `chat.js` – إرسال الرسائل ومتابعة المحادثات داخل الخيوط.
- `whatsappBot.js` – ربط البوت بتطبيق واتساب وتوجيه الرسائل.
- `index.js` – مثال مبسط لإضافة المنشآت وعرضها.
- المجلد `scripts/` يضم أوامر CLI مثل `createAssistant.js` و`uploadFile.js`.
- `logger.js` – تهيئة Winston لتسجيل الرسائل في ملفات `logs/`.
  يعتمد الآن على صيغة JSON مضغوطة مع تدوير تلقائي للملفات يوميًّا وحد أقصى للحجم.
- `metrics.js` – تعريف مقاييس Prometheus مثل عدد الطلبات وحالة الاتصال.
- `queue.js` – إنشاء طوابير BullMQ لرسائل واتساب والرسائل الجماعية.
- `scheduler.js` – تنفيذ المهام المجدولة وإرسال الرسائل في وقتها.
- `worker.js` – معالجة الرسائل من الطابور وإرسالها عبر واتساب.

## Running with Docker (mini)
1. Copy `.env.example` to `.env` and fill required secrets (database, Redis, OpenAI, `SESSION_SECRET`).
2. Start everything:
   ```bash
   docker compose up -d --build
   ```
3. Open the admin UI at `http://SERVER-IP:31371` (or your `APP_HOST_PORT`).
4. Run migrations when needed:
   ```bash
   docker compose run --rm migrate
   ```
5. View logs: `docker compose logs -f app` or `docker compose logs -f worker`.
6. Stop all services: `docker compose down`.

- Postgres (`db`) and Redis (`redis`) stay internal to the Docker network and are not published to the host.
- Override the host port by setting `APP_HOST_PORT` in `.env`; the app keeps listening on the internal `APP_PORT` (default `3001`).
